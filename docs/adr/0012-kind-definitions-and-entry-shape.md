# ADR-0012: 기록은 종류 id + 항목 값으로 저장하고, 종류 정의는 코드에 둔다

- **Status:** Accepted
- **Date:** 2026-11-02
- **Confidence:** Medium (종류 편집(R11 P2)을 아직 만들지 않아, 편집이 생겼을 때 기록을 옮기지 않아도 되는지는 그때 확인한다)

## Decision

**기록은 모든 종류에 공통인 칸과 `kindId`, `values`(항목 id → 값)로 저장한다. 종류·항목·값 목록은 코드의 정의 데이터(`DEFAULT_KINDS`)로 두고, 종류 편집(R11 P2) 때 사용자 정의(DB)를 합친다. 시각은 `timePrecision`(`exact` / `estimated` / `day`)으로 정확도를 나눈다.** 값 목록과 항목은 기획에서 아직 바뀌고 있고 나중에 사용자가 고칠 수도 있어서, 그때 저장된 기록을 옮기지 않기 위해서다.

## Context

- R11(P1)은 종류·항목·값 목록을 나중에 사용자가 고칠 수 있는 설정으로 다루고, 값이 추가되거나 항목이 늘어도 저장된 기록은 그대로 유지하라고 한다. 편집 화면은 P2다 (`docs/prd/R11.md`).
- R11의 기본 종류·항목 표는 초안이고 R11 계획 때 다시 검토한다 (`docs/prd/open-questions.md`). 사용자는 기획이 정리되지 않은 값 목록을 지금 맞추는 것은 의미가 없다고 봤다 (2026-11-02 대화).
- 바꾸기 전 `LogEntry`는 `kind` enum과 종류별 고정 칸(`stoolState`, `intensity`, `count`, `detail`, `riskFood`, `chocolateType`, `amountG`)을 가졌다 (`src/lib/domain/types.ts`, 2026-11-02 확인). 값 목록은 `src/lib/domain/values.ts`의 상수였다.
- 실제 사용자가 저장한 기록은 아직 없다. 화면은 가짜 데이터(`src/lib/mock/data.ts`)로 움직인다.
- 사용자는 배변 횟수를 "하루 전체 n회"와 "시각 + n회" 두 방식으로 기록하길 원했고, 하루 전체 기록을 모든 종류에 둘 수 있게 하기로 했다 (2026-11-02 대화). 바꾸기 전 기록은 시각과 `timeEstimated`만 있어 시각 없는 기록을 담을 자리가 없었다.

## Candidates

### 종류 정의를 두는 곳

#### A. 코드 (채택)
- 화면이 정의를 동기로 바로 읽는다. 편집 기능이 생기면 기본 정의(코드)와 사용자 정의(DB)를 합친다.

#### B. 지금부터 IndexedDB 정의 테이블
- 처음 열 때 기본 9개를 넣는다. 기본 정의가 바뀔 때마다 저장된 정의를 갱신해야 하고, 화면이 정의를 비동기로 불러와야 한다. 되돌리기 비싼 것은 기록의 모양이지 정의의 위치가 아니라서 탈락했다.

### 기록 모양

#### A. 공통 칸 + `kindId` + `values` (채택)
- 항목과 값을 라벨이 아니라 id로 저장한다. 라벨이 바뀌어도, 값이 추가돼도 기록은 그대로다.

#### B. 종류별 칸을 기록의 고정 칸으로 유지
- 타입이 단순하지만, 항목이 늘거나 종류 편집이 생기면 저장된 기록을 옮겨야 해서 탈락했다.

### 하루 전체 기록

#### A. 공통 칸 `timePrecision` (채택)
- `timeEstimated`(참/거짓)를 대신한다. `day`면 `occurredAt`은 기기 현지 시간대의 그날 0시다. 모든 종류에 쓸 수 있다.

#### B. 배변에만 "하루 전체" 항목
- 다른 종류에서 하루 기록이 필요해지면 기록 모양을 다시 바꿔야 해서 탈락했다.

## Evaluation

측정하지 않음.

## 확인하지 않은 가정

| ID | 가정 | 확인 방법 |
|---|---|---|
| A1 | 종류 편집이 생겨도 기본 정의(코드) + 사용자 정의(DB)를 합치는 것으로 충분하고 기록을 옮기지 않아도 된다 | R11 P2 계획 때 편집 동작을 정하고 이 모양에 맞춰 본다 |
| A2 | LLM 출력 스키마(값 목록 안에서만 고르기)를 정의에서 만들 수 있다 | R1 하위 작업 4(파싱 API)에서 만든다 |

## Consequences

- `src/lib/domain/kinds.ts`가 종류 정의의 원본이다. `values.ts`에는 종류와 무관한 값(날씨, 위험 등급, 모드, 종류 색)만 남는다.
- 기록 스키마는 모양만 검사하고 정의와 맞춰 보지 않는다. 정의로 값을 검사하는 일(`checkValues`)은 새로 저장하기 전에만 한다. 그래서 정의에서 빠진 id가 든 기록도 읽히고, 라벨 대신 id가 보인다.
- 값을 나누거나 없애면(예: `blood_mucus`를 혈변과 점액으로) 이미 저장된 기록의 옛 id를 어떻게 볼지 그때 정해야 한다.
- 칩의 `?` 표시(`UncertainField.field`)는 공통 칸 이름이나 항목 id를 가리킨다.
- 채팅 메시지 저장 모양은 ADR-0013이다. IndexedDB는 버전 2로 올리고 버전 1의 기록과 메시지는 지운다(개발 중 데이터뿐).
- 하루 전체 기록의 표시와 집계 방식은 `docs/prd/open-questions.md`에 남겼다.
- 맞바꾼 것: `values`의 키와 값을 TypeScript 타입이 보장하지 않는다. 코드는 `entry.values.stoolState`처럼 문자열 키로 읽고, 올바른 값인지는 정의 검사에 기댄다.

## Re-evaluation Triggers

- 종류 편집(R11 P2)을 계획할 때 (A1)
- `values`를 잘못된 키나 값으로 읽는 버그가 반복될 때
- 저장소를 서버나 앱(SQLite 등)으로 옮길 때
