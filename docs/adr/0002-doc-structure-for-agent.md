# ADR-0002: 문서 구조 — CLAUDE.md는 항상 필요한 것만, PRD는 영역별 파일로, 경로 규칙은 `.claude/rules/`로

- **Status:** Accepted (ADR 작성 시점 규칙은 ADR-0004로, 일정과 `docs/PLAN.md` 다루기는 ADR-0006으로 대체)
- **Date:** 2026-10-30
- **Confidence:** Medium (구조는 합의했지만, 읽는 양이 실제로 줄었는지와 규칙이 더 잘 지켜지는지는 아직 확인하지 않음)

## Decision

**모든 대화에서 읽히는 CLAUDE.md에는 항상 필요한 규칙만 두고, 나머지는 필요할 때 읽히는 곳으로 옮긴다.** PRD는 입구(`docs/PRD.md`)와 영역별 파일(`docs/prd/`)로 나누고, 특정 폴더에만 해당하는 규칙은 경로 규칙(`.claude/rules/`)으로, 문서로 지키기 어려운 규칙은 코드 검사로 옮긴다. 에이전트가 작업마다 읽는 양을 줄이고, 남은 규칙이 묻히지 않게 하기 위해서다.

## Context

- PRD가 316줄(약 38KB)로 커졌다. CLAUDE.md는 "관련 R 섹션만 읽는다"고 했지만, 파일 읽기 도구는 기본적으로 파일 전체를 읽는다.
- PRD 한 파일에 요구사항, 버전 기록, 일정(`docs/PLAN.md`와 겹치고 이미 어긋남), 열린 질문, 지표가 섞여 있었다.
- CLAUDE.md의 "반드시 지킬 규칙" 12개가 PRD 동작 명세를 다시 적은 것이었고, 작업 규칙과 코딩 규칙이 섞여 있었다. 낡은 정보(이미 없앤 페이지)와 package.json에 이미 있는 명령어 목록도 있었다.
- dev-log, ADR, PRD 수정을 언제 해야 하는지, 각 문서를 언제 읽는지 기준이 없었다.

## Candidates

### PRD 나누기
- **A. 영역별 5개 파일 (채택)**: `screens`(R0), `records`(R1·R2·R3·R8), `consult`(R4·R5), `safety`(R6), `platform`(R7·R9·R10). 사용자가 하는 일을 기준으로 나눠서 P2~P4 확장(음성, 첨부, 웹 검색 등)도 기존 영역에 들어간다.
- **B. 영역별 4개 파일**: R0을 기반 영역에 넣는 안. 화면이 늘면 R0이 커지는데 다른 R에 묻혀서 탈락했다.
- **C. 한 파일로 두고 부속 섹션만 빼기**: 파일 수는 적지만 요구사항만으로도 길어서 탈락했다.

### 버전 기록 / 일정 / 열린 질문 / 지표
- **버전 기록**: `docs/prd/changelog.md`로 분리 (채택). PRD 하단으로 옮기는 안, git 기록에만 맡기는 안은 탈락했다. 하단에 두면 매번 함께 읽히고, git 기록만으로는 결정 흐름을 보여주기 어렵다.
- **일정**: 마감일과 자르는 순서만 PRD에 남기고 날짜별 작업은 `docs/PLAN.md`로 모은다 (채택). 전체 삭제는 GitHub에서 우선순위가 안 보여서, 그대로 두기는 PLAN과 계속 어긋나서 탈락했다.
- **열린 질문**: `docs/prd/open-questions.md`로 분리하고 해결된 줄은 지운다 (채택). PRD에 두면 PRD가 자주 바뀌고, PLAN으로 옮기면 저장소에서 안 보여서 탈락했다.
- **지표**: `docs/metrics.md`로 분리한다 (채택). `metrics.csv`와 짝을 맞추기 위해서다. `docs/prd/metrics.md`는 csv와 폴더가 달라지고, PRD에 두면 dev-log를 쓸 때마다 PRD 전체를 읽어서 탈락했다.

### CLAUDE.md 규칙의 위치
- **설계 원칙 5개만 CLAUDE.md에 (채택)**: 기능을 계획할 때부터 필요한 "코드와 LLM의 역할 나누기" 원칙이다. 숫자·근거 카드, `assess()`, 고정 문장, 사전 우선, 이전 대화 제외가 여기에 해당한다.
- **경로 규칙으로 이동 (채택)**: 가드, 모델 환경변수, `NEXT_PUBLIC_` 금지, Dexie, 요청 제한은 `server.md`(새 파일)로 옮긴다. `values.ts` 목록 밖 값 처리, UTC 저장, 강아지 이름 규칙은 `domain.md`로 옮긴다.
- **삭제 (채택)**: 명령어 섹션(package.json에 있음, 환경변수는 README에 있음), 폴더 경계 섹션(폴더 이름으로 역할이 드러나고 import 규칙은 코드로 강제할 예정), 주의사항 섹션(위 규칙 파일로 옮기거나 낡은 정보라 삭제), "API 키는 서버에만"(`server.md`의 `NEXT_PUBLIC_` 규칙으로 대체).

### `docs/PLAN.md` 다루기
- **필요할 때만 읽고 요청받을 때만 고친다 (채택)**: 작업 결과는 dev-log에 남는다.
- **기능 단위 작업을 마치면 AI가 갱신**: dev-log와 같은 내용이 두 번 쌓여서 탈락했다.

### `/preview` 카탈로그
- **새 컴포넌트·상태는 카탈로그에도 추가 (채택)**: 규칙은 `styling.md`에 둔다. 요청받을 때만 추가하는 안과 카탈로그를 없애는 안은 탈락했다.

## 확인하지 않은 가정

| ID | 가정 | 확인 방법 |
|---|---|---|
| A1 | 작업 하나에서 읽는 양이 재편 전보다 줄었다 | 측정 방법 미정 |

## Consequences

- 기능 작업에서 읽는 PRD는 입구와 영역 파일 하나다. R 번호는 고정 ID라 파일을 옮겨도 바꾸지 않는다. 다른 영역은 다시 적지 않고 R 번호와 파일명으로만 가리킨다.
- PRD 색인의 "열린 질문" 칸에 표시된 R(R5, R6, R8)을 작업할 때만 열린 질문 파일을 읽는다. 블로킹 질문에 걸린 값은 지어내지 않는다.
- 지표 정의는 `docs/metrics.md` 한 곳에만 둔다. PRD Goals, dev-log, ADR은 ID만 적는다. 재는 대상이 바뀌면 새 ID를 만들고 옛 ID는 폐기로 표시한다.
- 기록 위치가 정해졌다. 제품 동작이 바뀌면 PRD + changelog, 기능 단위 작업이 끝나면 dev-log에 쓴다. 기술 결정은 세 조건 중 하나에 해당하면 ADR에 쓴다. 조건은 되돌리기 비쌈, 대안을 둘 이상 비교함, CLAUDE.md 규칙의 변경·예외다. dev-log 템플릿의 "계획" 칸은 승인 템플릿으로도 쓰고, "영향받는 지표"와 "결정할 것" 칸을 더했다.
- 맞바꾼 것: 문서 파일 수가 늘었다(PRD 1개 → 8개). 경로 규칙은 해당 경로의 파일을 다룰 때 읽혀서, 계획 단계나 새 파일을 처음 만들 때는 아직 읽히지 않았을 수 있다.
- 그 위험을 줄이려고 후속 작업을 정했다. 모든 `src/app/api/**/route.ts`가 `guardLlmRequest`를 부르는지 검사하는 테스트, `server-only`/`client-only` 도입 제안(스택 밖이라 별도 승인 필요), `src/lib/mock` import를 막는 ESLint 규칙(메인을 실제 저장소로 바꾼 뒤)이다.
- 남은 불일치: `docs/prd/platform.md` 기술 스택 표의 "필요 시 Zustand"와 CLAUDE.md의 "전역 상태 라이브러리는 쓰지 않는다"가 서로 다르다. → ADR-0003에서 쓰지 않는 쪽으로 정해 해결했다.

## Re-evaluation Triggers

- 영역 파일 하나가 PRD 원본 크기(약 38KB)에 가까워지거나, 기능 작업 하나가 영역 파일 세 개 이상을 늘 함께 읽어야 할 때
- 경로 규칙에 있던 규칙을 어긴 일이 dev-log의 "AI가 틀렸다가 고친 것"에 반복해서 나올 때 (CLAUDE.md로 되돌리거나 코드 검사로 바꾼다)
- 제출 후 여러 사람이 함께 작업하게 되어 PLAN.md 같은 개인 문서를 저장소에 올려야 할 때
