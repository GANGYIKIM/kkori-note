# ADR-0006: 계획 문서 구조 — plan.md는 큰 우선순위만, 세부 계획과 결과는 R 단위 dev-log에, `/planning`·`/next-plan`으로 다룬다

- **Status:** Accepted
- **Date:** 2026-10-30
- **Confidence:** Medium (구조는 대화로 합의했지만, 실제 R 작업에서 써 보지 않았고 `/next-plan`의 haiku 판단도 확인하지 않음)

## Decision

**`docs/plan.md`에는 큰 우선순위와 고르는 기준만 두고, 세부 계획과 결과는 R마다 폴더를 둔 dev-log 한 종류에 쌓는다.** 세부 계획은 `/planning <R> <하고 싶은 일>`로 세우고, 다음 할 일은 `/next-plan`으로 확인한다. 계획이 자주 바뀌어도 문서 종류가 늘지 않게 하고, 무엇을 할지 모를 때 전체 계획을 새로 짜는 비용을 피하기 위해서다. ADR-0002의 "일정"과 "`docs/PLAN.md` 다루기"를 대체한다.

## Context

- `docs/PLAN.md`에 날짜별 일정, 다음 할 일, 매일 마무리, 작업 기록이 함께 있었다. 사용자는 작업 기록이 계획 문서에 맞지 않는다고 봤다 (2026-10-30 대화).
- 사용자가 원하는 것은 우선순위에 따라 큰 계획을 대략 세우고, 명령어로 다음 할 일을 제안받는 것이다. 계획은 수시로 바뀐다.
- PRD 5장(마감과 자르는 순서)은 PRD에 둘 내용이 아니라고 사용자가 판단했다. 자르는 순서의 "시연영상·발표자료"는 개발 일이 아니라서 뺐다.
- dev-log는 "기능 하나 = 파일 하나, 날짜는 끝난 날"이었다 (`docs/dev-log/README.md`, ADR-0004). 별도 계획 문서를 더하면 계획 문서와 dev-log가 같은 일을 나눠 담게 된다.
- 커스텀 명령어는 `context: fork`로 떨어진 하위 에이전트에서 돌릴 수 있다 (anthropics/claude-code CHANGELOG 2.1.0, 2026-10-30 Context7로 확인). `` !`명령` ``으로 결과를 미리 넣으려면 `allowed-tools`에 그 명령을 허용해야 한다 (같은 저장소의 명령어 frontmatter 문서).

## Candidates

### 작업 기록
- **A. `docs/log.md`로 분리, 저장소 제외 (채택)**: 계획과 기록을 나눈다.
- **B. PLAN에 그대로 둠**: 계획 문서가 날마다 길어져서 탈락했다.

### 커밋한 일의 기록
- **A. 따로 기록하지 않음, git log가 맡음 (채택)**: `/next-plan`이 git log를 직접 읽는다.
- **B. git `post-commit` hook으로 커밋 제목을 PLAN에 붙임**: 비용은 0이지만 git log와 같은 내용이 두 번 쌓이고, amend·rebase 때 중복된다.
- **C. Claude Code hook으로 커밋마다 LLM 요약**: 커밋마다 비용이 들고 기록이 잘게 쪼개진다.

### `plan.md`의 내용
- **A. 큰 우선순위 + 고르는 기준 + R 문서 표 (채택)**: 파일 이름은 소문자 `plan.md`.
- **B. 날짜별 일정**: 자주 어긋나서 탈락했다.

### 세부 계획을 두는 곳
- **A. dev-log와 합침 (채택)**: 계획과 결과를 같은 문서에 쌓는다.
- **B. `docs/plans/`에 계획 문서를 따로 둠**: dev-log와 겹쳐 문서가 너무 많아진다는 사용자 지적으로 탈락했다.

### 문서 단위
- **A. R마다 폴더 + 수락 기준 묶음마다 하위 문서 (채택)**: R1이면 하위 문서 4~5개다. `CLAUDE.md`의 "기능 단위 = PRD 수락 기준을 하나라도 채우는 작업"과 같은 단위다.
- **B. R 하나 = 문서 하나**: 문서가 너무 길어진다.
- **C. PRD 줄 하나 = 문서 하나**: R1만 10개가 넘고, 서로 붙어 있는 줄(의도 나누기, 처리 순서, 바로 저장)을 따로 만들 수 없다.

### 다시 손볼 때
- **A. 같은 하위 문서의 "결과"에 날짜·커밋별로 이어 쓰고, 버전은 git이 맡음 (채택)**: 하위 문서 하나가 그 기능의 이력이 된다.
- **B. 다시 손볼 때마다 새 파일**: 문서 수가 늘고 이력이 흩어진다.

### `/next-plan` 실행 방식
- **A. haiku + `context: fork` + 필요한 내용 미리 넣기 (채택)**: 읽는 내용이 작고 판단이 단순해서 가장 싸다. 지금 대화도 길어지지 않는다.
- **B. 지금 대화의 모델로 실행**: 대화가 길수록 비싸다.

## Evaluation

측정하지 않음.

## Consequences

- 문서는 `plan.md`(큰 우선순위, 저장소 제외), R 문서(`docs/dev-log/R<n>/README.md`, 하위 작업 목록과 상태), 하위 문서(`docs/dev-log/R<n>/<slug>.md`, 계획과 이어 쓰는 결과)다. 작업 기록은 `docs/log.md`(저장소 제외)다.
- 상태는 한 곳에만 둔다. 하위 작업의 완료는 R 문서의 체크박스, R의 상태는 `plan.md` 표다.
- 고친 규모에 따라 처리한다. 작은 수정은 커밋만, 끝난 하위 작업을 다시 손보면 하위 문서에 결과를 이어 쓰고, 요구사항이 바뀌면 PRD와 changelog를 고치고 R 문서에 새 하위 작업 줄을 더한다.
- PRD 5장(마감과 자르는 순서)은 없앴다. 자르는 순서와 지키는 것은 `plan.md`에 있다.
- 기존 `2026-10-29-wide-screen-layout.md`는 옮기지 않고 dev-log 색인에 그대로 둔다.
- 맞바꾼 것: `plan.md`가 저장소에서 빠져 있어 GitHub에서는 우선순위가 보이지 않는다(ADR-0002가 PRD에 자르는 순서를 남긴 이유). 대신 R 문서와 하위 문서는 저장소에 올라간다.

## Re-evaluation Triggers

- R 하나의 하위 문서가 6개를 넘거나, 하위 문서 하나의 "결과"가 너무 길어져 읽기 어려울 때
- `/next-plan`의 제안이 사용자의 판단과 자주 다를 때 (모델을 sonnet으로 바꾼다)
- 제출 후 여러 사람이 함께 작업하게 되어 우선순위를 저장소에 올려야 할 때
