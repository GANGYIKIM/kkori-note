# ADR-0011: PRD는 R마다 파일 하나, 하위 요구사항과 수락 기준에 번호를 붙이고 검사 테스트로 빈 곳을 막는다

- **Status:** Accepted
- **Date:** 2026-11-01
- **Confidence:** Medium (R1 하나에만 적용해 봤고, 다른 R에서 번호 체계가 맞는지와 검사 테스트가 실제로 빈 곳을 잡는지는 아직 확인하지 않음)

## Decision

**PRD는 `docs/prd/R<n>.md`로 R마다 파일 하나에 두고, 하위 요구사항(`R<n>-k`)과 그 아래 수락 기준(`R<n>-k.m`)에 번호를 붙인다. 하위 요구사항마다 어떻게 만드는지는 R 문서의 "요구사항별 개발" 표에 적고, PRD·R 문서·테스트가 서로 어긋나면 `tests/requirements.test.ts`가 실패한다.** 기획이 명확해야 수락 기준에 구멍이 없고, 문서 사이의 연결은 사람이 맞추는 것보다 검사로 막는 편이 확실하기 때문이다.

ADR-0002의 "PRD는 영역별 파일로"를 대체한다.

## Context

- `/planning R1`(2026-11-01)에서 R1이 수락 기준 13개, 48줄로 커졌고, 에피소드를 R12로, 기록 종류를 R11로 떼어 냈다. 영역 파일 `docs/prd/records.md`는 R1·R2·R3·R8·R11·R12와 사용자 스토리, "나중에"를 담아 144줄이 됐다(2026-11-01 `wc -l`).
- 사용자는 기획 요구사항이 어떤 개발 함수에 대응하는지 나중에 쉽게 확인하기를 원했고, 검사 테스트가 요구사항을 다 덮지 못해 빈 곳이 생길까 걱정했다.
- R1을 검토하자 수락 기준이 없는 동작 문장이 3개 나왔다(한 문장에 기록 여러 개, 빈 칸 안내, 의도 미정 + LLM 실패). 수락 기준에만 번호를 붙이면 이런 문장은 검사에 잡히지 않는다.
- `/planning` 1단계는 PRD 색인의 "열린 질문" 칸이 비어 있지 않을 때만 `open-questions.md`를 읽는다(`.claude/commands/planning.md`). 다른 R의 일을 열린 질문으로 남겨도 색인 칸을 채우지 않으면 새 맥락의 계획에서 빠진다.
- CLAUDE.md는 타입, 함수, 테이블 같은 개발 내용을 PRD에 쓰지 않게 한다.

## Candidates

### 번호를 붙이는 단위
- **A. 하위 요구사항과 그 아래 수락 기준 모두 (채택)**: 동작 문장이 곧 하위 요구사항이 되고, 수락 기준이 그 아래에 모인다. 수락 기준도 "확인: R<x>"도 없는 하위 요구사항을 검사로 잡을 수 있다.
- **B. 수락 기준에만 번호, 빠진 수락 기준은 계획할 때 사람이 채움**: 번호 체계가 하나라 단순하다. 동작 문장과 수락 기준의 연결을 검사로 잡을 수 없어 탈락했다.
- **C. 동작 문장에 번호, 수락 기준 끝에 확인하는 동작 번호를 적음**: 검사는 가능하지만 PRD에 번호가 흩어지고 쓰는 규칙이 하나 늘어서 탈락했다.

### 개발 방법을 적는 곳
- **A. R 문서의 "요구사항별 개발" 표에 ID와 짧은 이름만 (채택)**: PRD에 개발 내용을 쓰지 않는 규칙을 지키고, PRD 문장을 옮겨 적지 않아 두 곳이 어긋나지 않는다.
- **B. R 문서 표에 PRD 수락 기준 문장을 그대로 옮김**: 문서 하나만 보면 되지만 PRD를 고칠 때마다 함께 고쳐야 해서 탈락했다.
- **C. 표만 두고 검사 테스트는 두지 않음**: 가볍지만 코드가 바뀌면 손으로 맞춰야 해서 탈락했다.

### PRD 파일 나누기
- **A. R마다 파일 하나, 이름은 `R<n>.md` (채택)**: 계획할 때 파일 하나만 읽고, dev-log의 `R<n>/`과 이름이 맞는다. R 제목이 바뀌어도 파일 이름은 그대로다.
- **B. records.md만 둘로 나눔**: 고칠 곳이 적지만 R 하나가 길어지는 문제는 그대로라 탈락했다.
- **C. 나누지 않음**: 계획할 때 R 섹션만 읽으니 읽는 양은 크게 늘지 않지만, 파일 단위 검사(색인과 파일 대조)가 어려워 탈락했다.

## Evaluation

측정하지 않음. 나누기 전 크기는 2026-11-01 `wc -lc`로 잰 값이다: records 144줄 / 18KB, consult 52줄, safety 43줄, platform 63줄, screens 24줄.

## 확인하지 않은 가정

| ID | 가정 | 확인 방법 |
|---|---|---|
| A1 | 하위 요구사항 번호 체계가 R1 밖의 R(특히 R5 표, R6 문장 표처럼 표가 많은 R)에도 무리 없이 맞는다 | 다음 R들을 `/planning`할 때 번호를 붙여 보고, 맞지 않으면 "AI가 틀렸다가 고친 것"에 남긴다 |
| A2 | 테스트 이름에 수락 기준 ID를 넣는 규칙이 지켜진다 | 체크된 수락 기준이 생길 때 검사 3이 실패하는지 본다 |

## Consequences

- PRD 형식: R 파일의 "요구사항 (P1)" 섹션에서 맨 앞 `-` 줄은 `- **R<n>-k 이름**: 동작`으로 시작한다. 그 아래 `- 수락 기준` 밑에 `- [ ] R<n>-k.m …`을 두거나, 다른 R에서 확인하면 `- 확인: R<x>…`를 둔다. 다른 R을 가리키기만 하는 문장은 `-` 없는 머리말로 쓴다.
- 기존 R은 `/planning`할 때 번호를 붙인다. 바꾸기 전에 지금 문장이 어디로 가는지 대응표를 보여주고, 바꾼 뒤 문장 단위로 대조한다. 번호가 없는 R은 검사 1·2를 건너뛴다.
- 테스트 이름은 확인하는 수락 기준 ID로 시작한다(예: `describe("R1-2.2 조회 질문은 기록을 만들지 않는다")`). 자동 테스트가 어려운 기준은 dev-log 하위 문서 결과에 `수동 확인: R<n>-k.m …`으로 남긴다.
- `tests/requirements.test.ts`가 검사하는 것: (1) 번호가 붙은 R에서 번호 없는 맨 앞 줄과 수락 기준 없는 하위 요구사항, (2) R 문서 "요구사항별 개발" 표와 PRD 하위 요구사항 ID의 차이, (3) 체크된 수락 기준이 테스트 이름이나 수동 확인에 없는 경우, (4) `open-questions.md`에 걸린 R인데 색인의 열린 질문 칸이 빈 경우, (5) 색인의 R 줄과 `docs/prd/R*.md` 파일의 차이.
- 맞바꾼 것: PRD 파일이 5개에서 13개로 늘었다. 사용자 스토리와 "나중에"가 R 파일로 흩어져, 영역 전체를 훑어보려면 여러 파일을 열어야 한다.

## Re-evaluation Triggers

- 번호 체계가 맞지 않는 R이 나와 예외 규칙을 두게 될 때
- 검사 테스트가 정상적인 문서를 자주 막아 우회 표시가 늘어날 때
- R 파일 대부분이 20줄 미만으로 작아 파일을 여러 개 함께 읽는 일이 잦아질 때
