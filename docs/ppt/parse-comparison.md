# 칩 만들기 방식 비교: 코드만 / LLM만 / 코드 + LLM

발표 자료(PPT)에 넣을 내용의 원본이다. 계획과 근거(1~5절), `npm run metrics`로 잰 결과와 해석(6~8절)을 담는다. 숫자는 측정값만 적는다.

- 작성: 2026-11-02
- 브랜치: `demo`
- 관련: CLAUDE.md 설계 원칙 4, PRD R1(R1-4 처리 순서)·R8, ADR-0001(모델과 가격), `docs/metrics.md`(M6, M7)

## 1. 한 줄 요약

채팅 한 문장을 기록 칩으로 바꾸는 세 방식을 같은 시험지 46문장으로 돌려 **정확도**와 **LLM 비용**을 비교한다. 지금 데모(LLM만)가 "개선 전", 코드가 먼저 채우고 못 채운 문장만 LLM에 보내는 방식이 "개선 후"다.

**결과**:
- 1차 비교: 코드 + LLM이 LLM 호출·비용·평균 응답 시간을 61% 줄였고, 정답률은 96.4% → 94.2%(46문장 중 1문장 차이)였다.
- 원인 분석: 틀린 원인은 코드가 "다 채웠다"고 자신한 문장 중 틀린 2문장(확신 오답)이었다.
- 두 번째 개선: 확신 오답 규칙과 프롬프트 줄을 더한 뒤 최종 결과는 정답률 100%, 비용 −56%, 응답 시간 −58%(데모 대비)다. 같은 시험지로 고치고 잰 결과라 과적합 가능성이 있다(9절).

## 2. 배경: 무엇을 비교하나

꼬리노트는 보호자가 채팅으로 보낸 문장을 기록 칩으로 저장한다.

| 보낸 문장 | 저장되는 칩 |
|---|---|
| 방금 응가했는데 좀 무른 편이야 | 배변 · 상태 무름 · 횟수 1회 · 지금 |
| 아침 8시에 밥 먹고 산책 다녀왔어 | 식사 · 08:00 / 산책 · 08:00 |
| 천둥 쳐서 5분 동안 떨었어 | 천둥 떨림 · 5분 |

문장을 칩으로 바꾸는 방법은 셋이다.

### 방식 1. 코드만

- 키워드 사전(`lexicon.ts`)과 시각 파서(`time-parse.ts`)가 칩을 채운다 (`extractEntries`).
- 사전에 있는 표현만 알아본다. "무른 편", "흐물흐물", "물렁해" → 무름.
- LLM을 부르지 않으니 비용이 0이고 즉시 끝난다.
- 사전에 없는 표현, "어제 저녁" 같은 시각, 질문인지 기록인지는 판단하지 못한다.
- main 브랜치에 구현·테스트되어 있지만 화면에는 연결되지 않았다.

### 방식 2. LLM만 (지금 데모)

- 메시지마다 LLM(gpt-6-luna)을 한 번 불러 의도·답변·강아지 이름·기록 칩을 한꺼번에 받는다.
- LLM에는 기록 종류와 값 목록을 주고 그 안에서만 고르게 한다. 목록 밖 값은 코드가 버린다(`toDrafts`).
- 표현이 다양해도 잘 알아듣지만, 모든 메시지가 비용과 대기 시간을 쓴다. LLM이 실패하면 기록이 저장되지 않는다.
- 데모 일정 때문에 이 방식을 택했다. 설계 원칙 4("칩이 다 채워지면 LLM을 부르지 않는다")와 어긋나는 맞바꿈이다.

### 방식 3. 코드 + LLM

- 코드가 먼저 채우고, 다 채웠으면 LLM을 부르지 않는다. 못 채웠을 때만 LLM을 부른다.
- 설계 원칙 4가 원래 의도한 방식이다.
- LLM을 부르는 방법에 따라 A와 B로 나뉜다(3절).

## 3. 코드 + LLM의 두 가지: A(라우터)와 B(빈 칸만)

| | 코드가 다 채웠을 때 | 코드가 일부만 채웠을 때 |
|---|---|---|
| A 라우터 | LLM을 부르지 않음 | 코드 결과를 버리고 LLM이 처음부터 다 함 (지금 데모 프롬프트 그대로) |
| B 빈 칸만 (main 설계) | LLM을 부르지 않음 | 코드가 채운 칩은 고정하고, LLM은 빈 칸만 값 목록에서 고름 |

예시 문장 "어제 저녁에 응가했는데 무른 편이야":

- 코드는 배변과 상태 "무름"을 채우지만 "어제 저녁"은 읽지 못해 LLM이 필요하다고 표시한다.
- A: LLM이 문장 전체를 다시 해석한다. 상태를 "보통"으로 잘못 고르면 코드가 맞힌 값까지 틀린다.
- B: LLM은 시각만 채운다. 배변 · 무름은 코드 값 그대로다.

두 방식의 차이:

| | A | B |
|---|---|---|
| LLM 호출 수 | 코드가 못 채운 문장 수 | A와 같음 |
| 토큰 | 지금 데모와 같음 | 적음. 출력이 빈 칸뿐이고, 프롬프트에 관련 종류만 넣을 수 있음 |
| 정확도 | 일부만 채운 문장에서는 "LLM만"과 같음 | 일부만 채운 문장에서 코드가 맞힌 값을 지킴 |
| 만드는 품 | 지금 프롬프트를 그대로 씀 | "코드가 채운 칩 + 빈 칸 목록"을 받는 새 프롬프트와 결과를 합치는 코드 필요 (약 1시간 추가) |

**진행 순서**: A로 먼저 측정해 "LLM 호출과 비용이 얼마나 주는지"를 확인한다. 결과를 보고 B를 다음 단계로 제안한다. B는 호출 수가 아니라 토큰과 정확도에서 이득을 노린다.

## 4. 질문 문장 처리

코드에는 의도 나누기(기록인지 질문인지)가 없다. 그래서 "어제 응가 몇 번 했어?"를 코드가 배변 기록으로 저장해 버릴 수 있다. A에서는 아래 규칙에 걸리면 코드가 다 채웠어도 LLM으로 보낸다(`chooseParser`).

- `?`가 있다
- 문장 끝이 `까`, `니`, `나요`, `가요`, `죠`, `냐`, `어때`
- `몇`, `언제`, `왜`, `어떻게`, `얼마나`, `어땠`이 있다

규칙이 틀려도 LLM으로 더 보낼 뿐(비용 증가) 잘못 저장하지는 않는 쪽으로 기운다.

### 채점

문장 하나가 정답이려면 아래를 모두 만족해야 한다.

- 기록 종류 묶음이 정답과 같다 (빠지거나 더 생기면 오답)
- 정답에 적은 칸(예: 배변 상태)의 값이 같다. 정답에 적지 않은 칸은 보지 않는다
- 정답에 시각(`08:00` 또는 "하루 전체")이나 지속시간을 적었으면 그것도 같다

의도, 답변 문장, 강아지 이름 저장은 채점하지 않는다. 기록 칩만 본다.

### 실행

- `npm run metrics` 한 번으로 세 방식을 모두 돈다.
- LLM은 앱과 같은 함수(`callChatLlm` → `toDrafts`)로 부른다. 배포 라우트를 거치지 않는 이유는 요청 제한(IP당 하루 30회)에 걸리기 때문이다.
- LLM 결과는 매번 조금씩 달라서 3번 돌려 평균을 낸다.
- 코드 + LLM(A)은 LLM을 따로 더 부르지 않는다. 문장마다 `chooseParser`가 "코드"라고 하면 코드 결과를, "LLM"이라고 하면 같은 실행의 LLM 결과를 쓴다.
- 비용 = 입력 토큰 × $0.10/1M + 출력 토큰 × $0.50/1M. gpt-6-luna 가격으로, ADR-0001에서 2026-10-29에 OpenAI 공식 가격 페이지로 확인한 값이다.

| 오늘은 비 와서 산책 못 했어 | 세 방식 모두 (0/3) | **확신 오답**이면서 LLM도 틀림. "못 했어"를 산책 기록으로 남긴다 |
| 이따 저녁에 산책 갈 거야 | 코드만, LLM 1/3 틀림 | 앞으로 할 일인데 LLM이 가끔 기록으로 남긴다 |
| 동물병원 번호 010-1234-5678 기억해 줘 | LLM 1/3 틀림 | LLM이 한 번은 기록을 만들었다. 전화번호가 기록에 들어갈 수 있다 |
| 응가에 피가 묻어 나왔어, 부정·반대 2문장, 사전에 없는 일 2문장, 질문, 비속어 + 사건, poop, 💩, 시각이 다른 여러 기록, "아침 8시" | 코드만 | 사전에 없는 표현이라 코드가 칩을 다 못 채움. 코드 + LLM에서는 LLM으로 넘어가 모두 맞힘 |

## 7. 결과를 읽는 법

- **비용과 속도는 크게 줄었다.** 46문장 중 28문장(61%)을 코드가 끝내서 LLM 호출·비용·평균 응답 시간이 모두 61% 줄었다.
- **정확도는 1문장만큼 낮아졌다.** 코드가 "다 채웠다"고 한 28문장 중 2문장이 틀렸다(확신 오답). 그중 "산책 못 했어"는 LLM도 틀려서, 코드 + LLM 때문에 생긴 손해는 "옆집 개가 설사했대" 하나다.
- **처음 30문장만으로는 이 문제가 안 보였다.** 시험 실행에서 30문장일 때는 확신 오답이 0건이었다. 사전 코드를 보고 쓴 문장이라 그랬고, 엣지 케이스 16문장을 더하자 2건이 나왔다. 시험지를 만든 쪽(AI)이 채점 대상(사전)을 알고 있으면 시험지가 쉬워진다는 사례다.
- **코드만으로는 부족하다.** 71.7%. 부정 표현, 사전에 없는 일, 영어·이모지에서 0점이다.
- **LLM에도 약점이 있다.** 안 한 일·계획을 기록으로 남기고, 전화번호가 든 문장을 기록으로 만들기도 한다.

## 9. 두 번째 개선: 확신 오답 고치기

### 바꾼 것

1차:
- `chooseParser`에 신호를 더했다. 아래 표현이 있으면 코드가 다 채웠어도 LLM으로 보낸다 (`mentionsNotDoneOrOthers`).
  - 다른 개: `옆집`, `남의`, `다른 개·강아지`, `친구네`, `친구 개·강아지`
  - 전해 들은 말: 문장 끝 `대`, `래`
  - 하지 않은 일: `못·안` + `했·먹·쌌·갔·나갔`, `않았`
  - 앞으로 할 일: `거야`, `거예요`, `할게`, `갈게`, `려고`, `예정`
- LLM 프롬프트에 한 줄을 더했다: "이 강아지에게 실제로 있었던 일만 남긴다. 하지 않은 일, 앞으로 할 일, 다른 개의 일은 기록하지 않는다."

2차:
- 1차 프롬프트 때문에 "시발 옆집 강아지가 우리 개를 물었어."를 LLM이 3번 중 2번 기록하지 않았다(수정 전 3/3). "다른 개의 일"을 우리 개가 물린 일에까지 적용한 것이다.
- 프롬프트에 "다만 다른 개 때문에 이 강아지에게 생긴 일("옆집 개가 우리 개를 물었어")은 기록한다"를 더했다.

### 결과 (같은 시험지 v1, LLM 3회 평균)

| 단계 | LLM만 정답률 | 코드 + LLM 정답률 | 코드 + LLM 호출 | 코드 + LLM 1,000개당 비용 | 코드 + LLM 평균 응답 시간 | 확신 오답 |
|---|---|---|---|---|---|---|
| 수정 전 | 96.4% | 94.2% | 18회 | $0.0661 | 578ms | 2 / 28 |
| 1차 | 98.6% | 98.6% | 20회 | $0.0744 | 636ms | 0 / 26 |
| 2차 | 99.3% | **100%** | 20회 | $0.0759 | 620ms | 0 / 26 |

- 확신 오답이던 두 문장은 이제 LLM으로 넘어가고, LLM도 프롬프트 줄 덕분에 맞힌다.
- LLM으로 넘어가는 문장이 18 → 20개로 늘어 비용이 조금 늘었다. 프롬프트가 길어져 호출당 입력 토큰도 약 1,370 → 1,460개로 늘었다.
- 2차에서 LLM만 쓴 방식은 "오늘 하루 종일 설사했어"를 3번 중 1번 틀렸다. 코드 + LLM에서는 이 문장을 코드가 처리한다.

### 처음(데모)과 최종 비교

| | 데모 (LLM만, 수정 전) | 최종 (코드 + LLM, 2차) | 변화 |
|---|---|---|---|
| 정답률 (M6) | 96.4% | 100% | +3.6%p |
| LLM 호출 | 46회 | 20회 | −57% |
| 1,000개당 비용 (M7) | $0.1713 | $0.0759 | −56% |
| 평균 응답 시간 | 1,471ms | 620ms | −58% |

- 비용·시간 감소는 코드가 먼저 처리하는 구조(라우팅)에서 왔다.
- 정답률 상승은 프롬프트 줄(LLM만 쓴 방식도 96.4% → 99.3%)과 라우팅 규칙에서 함께 왔다.

### 주의: 같은 시험지로 고치고 같은 시험지로 쟀다

1차 규칙과 프롬프트는 틀린 두 문장을 보고 만들었다. 그래서 100%는 이 시험지에 맞춘 결과일 수 있다(과적합). 규칙이 일반적으로 통하는지는 이 규칙을 보지 않고 쓴 새 문장으로 확인해야 한다. 테스트에는 시험지에 없는 표현(`친구네 강아지가 토했어`, `밥을 안 먹었어`, `내일 병원 갈 예정이야` 등)을 넣었다.

## 10. 한계

- 시험지 46문장은 직접 만들었다. 실제 사용자 문장 분포와 다를 수 있다.
- 기록 칩만 채점한다. 답변 문장의 품질과 이름 저장은 보지 않는다.
- LLM은 3번 평균이라 문장 하나의 흔들림은 남는다. 같은 조건의 두 실행에서 LLM만 쓴 정답률이 97.8%와 96.4%로 달랐다.
- 문장 1개가 2.2%p라서, 정답률 차이는 문장 수로 읽어야 한다.
- 응답 시간은 개발 PC에서 OpenAI를 직접 부른 값이다. 배포 환경의 네트워크 시간은 다를 수 있다.
- 가격은 2026-10-29 공식 페이지 기준이다. 추론 토큰은 출력 토큰에 포함되어 계산된다(데모 기본 추론 강도는 none).
- 질문 규칙과 남의 일·안 한 일 규칙은 단순한 문자열 규칙이라 의도 나누기(R1 하위 작업 3)를 대신하지는 못한다. 규칙이 틀리면 LLM으로 더 보낼 뿐이라 비용만 늘어난다.
- 두 번째 개선은 틀린 문장을 보고 고친 뒤 같은 시험지로 쟀다. 최종 100%는 과적합일 수 있다(9절).
- 데모 화면에는 아직 코드 + LLM이 연결되지 않았다. 측정은 같은 함수로 했지만, 앱은 지금도 메시지마다 LLM을 부른다. 프롬프트 줄은 앱에도 들어갔다.
