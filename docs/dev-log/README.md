# dev-log

기능 작업의 계획과 결과. R마다 폴더를 두고, 찾을 때는 아래 색인 → R 문서 → 하위 문서 순서로 필요한 파일만 연다. 근거는 ADR-0006.

## 구조

- **R 문서** `R<n>/README.md`: 그 R의 목표, 블로킹 질문, 하위 작업 목록과 상태. 형식은 `TEMPLATE-R.md`. `/planning`이 만든다.
- **하위 문서** `R<n>/<영어-slug>.md`: 수락 기준 묶음 하나의 계획과 결과. 형식은 `TEMPLATE.md`. 날짜는 파일 이름에 넣지 않고 본문에 쓴다.
- 여러 R에 걸친 작업은 주된 R의 폴더에 두고, 본문의 R 칸에 함께 적는다.
- R에 속하지 않는 작업(개발 도구, 문서 구조)은 이 폴더 바로 아래 `YYYY-MM-DD-<영어-slug>.md`로 둔다. 형식은 `TEMPLATE.md`이고, 날짜는 시작한 날이다.

## 쓰는 법

- 하위 작업을 시작할 때 하위 문서를 만들고 "계획"을 쓴다. 승인 요청도 이 형식으로 한다. 만들면 바로 R 문서의 그 줄에 링크한다(빠뜨리면 `tests/docs-index.test.ts`가 실패한다).
- 하위 작업을 마치면 "결과"에 날짜·커밋과 함께 쓰고, R 문서에서 그 줄을 체크한다. R의 하위 작업이 모두 끝나면 `docs/plan.md` 작업 표의 상태를 "완료"로 바꾼다.
- 하위 작업이 6개를 넘으면 R 문서를 나누자고 제안한다.

## 다시 손볼 때

| 고친 규모 | 처리 |
|---|---|
| 작은 수정 (오타, 문구, 한 곳 리팩터링) | 문서는 그대로 둔다. 커밋 메시지로 충분하다 |
| 끝난 하위 작업을 다시 손봄 (버그 수정, 동작 개선) | 같은 하위 문서의 "결과"에 날짜·커밋과 "왜"를 붙여 항목을 더한다 |
| 요구사항이 바뀜 | PRD와 `prd/changelog.md`를 고치고, R 문서에 새 하위 작업 줄을 더한다 |

예전 내용은 `git log -p <파일>`로 본다. 큰 기술 결정을 뒤집으면 ADR을 쓰고 하위 문서에는 링크만 남긴다.
